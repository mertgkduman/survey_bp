# Stack Research: Policy-Based BP Research Platform for QLDPC Decoding

**Domain:** Reproducible scientific software for BP-family quantum LDPC decoding  
**Researched:** 2026-09-21  
**Overall confidence:** MEDIUM. The research-plan seam selected Context7 for library questions, but neither its MCP tools nor the documented `ctx7` CLI is available here. I used current official project documentation, repositories, and PyPI release records through the web-search fallback. The confidence seam rates cross-checked web-search findings MEDIUM. Version candidates below are **observed releases, not installed packages or locked project dependencies**.

## Recommendation

Build a small, installable **Python 3.12 package** for experiment definitions, an interpretable reference implementation of each compatible BP kernel family, provenance, and analysis. Use NumPy and SciPy for arrays and sparse parity checks. Keep the canonical decoder loop owned by this project: an external decoder's public `decode` call cannot expose arbitrary update, schedule, state, intervention, and work-accounting policies. Add a compiled kernel only after a benchmark identifies a specific hot loop and the Python path remains the executable specification. Python 3.12 is a proposed portability baseline, not a requirement already established by the project; the release records below show candidate support, while the cluster Python/glibc toolchain still needs checking. [NumPy releases](https://pypi.org/project/numpy/), [SciPy releases](https://pypi.org/project/scipy/), [ldpc releases](https://pypi.org/project/ldpc/). **Confidence: MEDIUM.**

Use `ldpc`/BP-OSD/BP-LSD and paper repositories as **versioned reference executions and comparison points** behind narrow adapters. The current `ldpc` repository says v2 is a C++/Cython rewrite and warns of possible v1 compatibility breaks; its published docs demonstrate `BpDecoder`, `BpOsdDecoder`, `BpLsdDecoder`, syndrome decoding, and parallel/serial schedules. This is a useful reference surface, but the docs are labeled 2.1.0 while PyPI currently lists 2.4.1, so every API and numerical assumption needs a test against the pinned artifact. [ldpc repository](https://github.com/quantumgizmos/ldpc), [BP docs](https://software.roffe.eu/ldpc/bp_decoding_example.html), [quantum decoder docs](https://software.roffe.eu/ldpc/quantum_decoder.html), [PyPI](https://pypi.org/project/ldpc/). **Confidence: MEDIUM.**

## Reproducibility and storage choices

Use a source-controlled `pyproject.toml` with a standard build backend (start with Hatchling for a pure-Python package), optional dependency groups for reference decoders, circuit simulation, and docs, and a command-line entry point that accepts a manifest. Generate an environment lock or exact constraints **after** validating on the target HPC image; store the resolved packages, platform, executable revision, and reference commit in each run record. The Python Packaging User Guide identifies `pyproject.toml` as the standard configuration and describes Hatchling as a build backend. [Packaging guide](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/), [Hatchling release](https://pypi.org/project/hatchling/). **Confidence: MEDIUM.**

Define separate schema-versioned records for (1) paper/reproduction manifest, (2) run/job metadata, (3) shot outcome, and (4) decoder events/work. Require immutable IDs linking code and logical-operator hashes, noise/sample IDs, policy configuration, RNG derivation, backend version, and any post-selection decision. For HPC, write bounded per-job Parquet shards and publish a completion marker/metadata only after a successful close; aggregate afterward, rather than having many array workers append to one file. JSON is appropriate for small human-reviewable manifests and discrepancy notes. PyArrow has explicit schemas and partitioned datasets, but the exact ledger layout and crash recovery protocol are project design decisions still to validate. [Arrow dataset docs](https://arrow.apache.org/docs/python/getstarted.html), [Parquet docs](https://arrow.apache.org/docs/python/parquet.html). **Confidence: MEDIUM.**

Use NumPy's `SeedSequence` or equivalent deterministic derivation from stable experiment/sample identifiers so that paired decoder runs consume the same generated error samples regardless of Slurm array width. Materialize or hash shared sample batches for controlled comparisons, because a common numeric root seed alone does not guarantee identical sampling across different consumption order. NumPy documents deterministic parallel stream derivation; the paired-sample requirement is a project inference. [NumPy parallel RNG](https://numpy.org/doc/stable/reference/random/parallel.html). **Confidence: MEDIUM.**

Submit sweep units as scheduler job arrays where the site supports Slurm; include array index and manifest ID in each shard and obey local array and filesystem limits. Slurm's official docs describe arrays as collections of similar batch jobs with common initial resource options. Do not make Slurm a runtime dependency of the decoder library: a local single-process runner should use the same manifest. [Slurm job arrays](https://slurm.schedmd.com/job_array.html). **Confidence: MEDIUM.**

## Development and documentation tools

Use pytest (observed 9.1.1) for deterministic algebraic/kernel tests, small exhaustive-code checks, schema round trips, reference adapter smoke tests, and statistical reproduction tests with declared confidence intervals. Use Ruff (observed 0.16.8) for lint/format and a static type checker for contracts. Test each policy composition against algebraic invariants and an independently computed syndrome/logical outcome; speed benchmarks are separate from correctness gates. [pytest release](https://pypi.org/project/pytest/), [parametrization docs](https://docs.pytest.org/en/stable/how-to/parametrize.html), [Ruff docs](https://docs.astral.sh/ruff/). **Confidence: MEDIUM** for tools; test design is a project recommendation.

Use Sphinx with MyST Markdown for mathematical definitions, policy compatibility tables, API reference, manifests, reproduction recipes, and known discrepancies. Sphinx supports mathematics and MyST-based Markdown. Keep published experiment tables/figures generated from ledger queries rather than maintained by hand. [Sphinx math](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html), [Sphinx Markdown](https://www.sphinx-doc.org/en/master/usage/markdown.html). **Confidence: MEDIUM.**

## Alternatives and exclusions

| Choice | Use alternative when | Current decision |
|---|---|---|
| Pure Python canonical kernel vs immediate C++/Cython rewrite | Profiling shows a specific BP operation dominates representative workloads and correctness parity is demonstrated. | Start with inspectable Python; optimize only the measured seam. |
| PyArrow/Parquet vs CSV-only or database-first ledger | CSV can serve tiny exports; a database becomes useful if concurrent interactive queries become a real need. | Typed, per-job Parquet shards serve high-volume analysis and keep deployment simple. Sinter CSV remains a supplementary aggregate, not the event ledger. [Sinter API](https://github.com/quantumlib/Stim/blob/main/doc/sinter_api.md). |
| `ldpc` as canonical engine vs reference | If a specific published experiment requires exact implementation behavior, execute its pinned source in the reference lane. | The project owns its policy kernel; do not infer arbitrary composability from existing constructor options. |
| Stim/Sinter from day one vs circuit stage | Early smoke tests can verify import and format assumptions. | Keep circuit packages optional until circuit semantics are specified; CSS code-capacity need not inherit detector-event conventions. |
| GPU/PyTorch/JAX framework | Only if a concrete batched algorithm and benchmark shows a benefit while preserving policy observability. | No GPU framework in the initial stack; it would add kernel and reproducibility complexity without an established requirement. |

## Roadmap implications and unresolved checks

1. **Foundation:** decide canonical matrix/bit ordering and hash serialization, manifest and ledger schema versions, RNG sample identity, package build, local runner, tests, and docs. Validate target cluster Python/glibc/wheel compatibility and create a real lock.
2. **CSS engine and references:** implement a transparent binary policy kernel; pin and smoke-test `ldpc` 2.4.1 and any paper-specific `bposd` environment. Check schedule/update semantics, decoder status, and BP-LSD parameter spelling against the installed artifact. Keep reference measurements and canonical traces distinctly labeled.
3. **BP policies and optional postprocessing:** establish policy compatibility and work units before using compiled optimizations. Benchmark representative codes/schedules, then consider scikit-build-core only for a stable hot loop.
4. **Quaternary and circuit extensions:** add separate correlated kernel semantics, then Stim/Sinter as circuit inputs/benchmarks. In circuit work, research DEM conversion, correlated mechanisms, detector/observable conventions, and Sinter's aggregate-only record before adopting any adapter.

**Open checks:** authoritative versions/commits and licenses for RelayBP, BPGD, impulse, and BeamSearch references; exact `ldpc` 2.4.1 API/ABI behavior; portability of PyArrow and Stim wheels to this HPC system; workload size and storage quotas; choice of type checker; final schema and statistical acceptance criteria. No project dependencies are locked or installed on the basis of this research.
