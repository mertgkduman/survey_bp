# Bounded BP kernel efficiency check — 2026-10-19

## Result

The policy-composable architecture is useful for specifying and auditing decoder behavior, but the current Python execution engines are not fast enough for large simulation campaigns. On this node, matched binary SPA decoding took about **2,200×** as long as the `ldpc` compiled decoder, and matched early-stop GB46 BP4 took about **7,560×** as long as the pinned aSCED C++ BP4 decoder. These are local throughput measurements, not published performance or curve-reproduction results.

| Family and workload | Project kernel, median ms/shot | Native kernel, median ms/shot | Output check | Ratio |
|---|---:|---:|---|---:|
| BB72 `hz`, binary SPA, `p=.08`, cap 10, 24 syndromes | 192.921, cached graph | `ldpc` SPA 0.0876 | 24/24 candidates and iteration counts equal | 2,202× |
| BB72 `hz`, binary min-sum, same inputs | 56.288, cached graph | Relay Rust trace 0.0349; `ldpc` min-sum 0.0278 | Project candidate digest differs; Relay and `ldpc` agree | No matched-output ratio |
| GB46 H44, four-state BP4, `p=.08`, cap 8, eight syndromes, early stop | 1,519.609 | aSCED C++ BP4 0.2010 | 8/8 candidates agree; successful stop iterations agree | 7,561× |
| GB46 H44, four-state BP4, eight forced sweeps | 2,693.614 | aSCED C++ BP4 0.3079 | 4/8 final candidates agree | No matched-output ratio |

Three batch repetitions are retained in [results.json](./results.json), with per-shot candidates, success flags, iteration counts, and individual times. Ratios use medians of the three batch times. For aSCED C++ capped runs, its `BP_Parallel` loop leaves the public `iteration` counter at 9 after eight sweeps; this is a loop-counter convention, not a ninth sweep. Native output labels `I,X,Z,Y` were translated to the project's `I,X,Y,Z` before candidate comparison. The early-stop BP4 agreement on eight samples does not establish agreement on all inputs.

## Conditions and interpretation

- One Intel Xeon Gold 6248R node (`dcc-core-ferc-u-ac39-4-1`), Python 3.12.2, `OMP_NUM_THREADS=1`, OpenBLAS/MKL thread counts 1, process affinity CPUs 46 and 94. Work ran on a shared HPC node; no exclusive core reservation or CPU frequency control was available. This is a development benchmark.
- BB72 input is the checked-in `data/artifacts/bb72-css.json` `hz` matrix (72 variables, 216 edges). GB46 uses the pinned H44 aList (46 variables, 352 edges). Seed 11019 generated immutable error/syndrome arrays; physical error rate was 0.08. Priors, flooding schedule, and caps are declared in [benchmark_bp_kernels.py](../../../scripts/benchmark_bp_kernels.py).
- Timed batches exclude decoder graph construction for native implementations. The project binary rows include both public `run` and a cached `EdgeTable`/`FloodingSchedule` path. Caching changes SPA 193.751 to 192.921 ms/shot and min-sum 57.474 to 56.288 ms/shot, so repeated graph construction explains little of the gap. The project BP4 batch includes per-shot problem/session construction; a separate 100-session local check measured about 4.1 ms/setup, small against 1.52–2.69 seconds/shot. Native C++ timing excludes graph construction.
- The C++ path is ordinary BP4 from the aSCED repository, built `Release`/`-O3` with OpenMP and one thread. It is **not** the full aSCED ensemble and does not change Phase 11's `preserve_unavailable` decision on matched native source reproduction. The Rust path is Relay-BP `MinSumBPDecoderTraceF64` with `alpha=None`, `gamma0=None` (source default plain min-sum); `ldpc` is 2.4.1 with parallel SPA/min-sum and one thread.
- This is not a cross-family speed ranking: binary and four-state BP perform different work. The two matching-output ratios above are useful engineering throughput checks for their respective workloads. The min-sum and forced-sweep BP4 ratios are intentionally withheld because outputs differ.

## Bottleneck evidence

[profile.txt](./profile.txt) contains a bounded `cProfile` sample generated by [profile_bp_kernel_hotspots.py](../../../scripts/profile_bp_kernel_hotspots.py). One BB72 SPA sweep made 216 per-edge check calls, with 864 scalar `boxplus_pair` calls and 2,602 `finite_saturate` calls; check update and small-array validation dominate. One GB46 BP4 sweep made 2,464 `commutation_llr`, 4,576 `anticommutes`, and 15,320 `finite_saturate` calls. The four-state sweep also searches check/variable membership with `np.flatnonzero` inside edge loops. These call counts explain why reusing graph objects alone yields little benefit. The profile is diagnostic, not a calibrated timing comparison.

## Engineering decision

Keep one canonical behavioral engine per compatible family and its policy/provenance contract. Move the admitted inner flooding loop to a compiled, graph-indexed backend: precompute check/variable adjacency once, resolve policy parameters to fixed arrays before each run, and execute contiguous message buffers with Python outside the hot loop for manifests, ledger emission, and independent evaluation. Start with plain binary SPA and four-state BP4, then add min-sum and named policies through the same engine. Preserve a Python reference mode for differential tests and interpretation.

Before replacing the kernel, isolate the BB72 min-sum mismatch and the GB46 post-convergence forced-sweep mismatch at intermediate C2V/V2C/belief buffers. Require candidate, convergence, iteration, and numerical-boundary agreement for the selected policy profile; only then compare runtime at matched work and budget. Repeat on dedicated CPUs with larger BB144/HGP and Toric/GB46 graphs, report memory and setup separately, and benchmark full decoder/ledger throughput as well as inner sweeps. The present numbers support prioritizing a compiled kernel; they do not determine whether Rust, C++, or another compiled backend is best.

## Reproduction

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 \
  .venv/bin/python scripts/benchmark_bp_kernels.py --output /tmp/bp-kernel-results.json
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
  .venv/bin/python scripts/profile_bp_kernel_hotspots.py
```

The benchmark script expects the pinned aSCED checkout/build under `/tmp/phase10-asced-native/`; source commit `816772071486615dfc7d71d1e15df597edc58a26`. Relay source checkout commit was `8216aca3153642044e2cdccbaa41547d15551bb0`. The native driver is [benchmark_asced_bp4.cpp](../../../scripts/benchmark_asced_bp4.cpp). This path dependency is explicit and should be parameterized for a portable performance suite.
